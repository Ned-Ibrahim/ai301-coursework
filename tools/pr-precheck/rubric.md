# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-within-plan | Every changed file and every hunk in the diff, and every commit message, read against the plan's scope statement, the files it names, its not-in-scope line, and its deviation notes (evidence guide: Plan fidelity) | Passes if every hunk does work the plan names or a deviation note in the plan records: the planned change itself, a test of the planned behavior, or an edit to a file the plan names for that change. These also count as planned: a hunk the repo's stated asks require for this change (a changelog or whatsnew entry, an i18n string, a regenerated file, removing the xfail marker or lint suppression that names the fixed bug), an import the planned change needs, and a code comment explaining the change. Fails if any hunk does work the plan neither names nor records as a deviation: a new feature, flag, option, setting, or config field; a rename, refactor, or rewrite of code the fix does not need; a wording change to text the fix does not touch; an edit to a file outside the plan's named files that no deviation note covers; or anything the plan's not-in-scope line excludes. A commit message announcing such work ("add a --verbose-errors flag", "rename handlers for consistency") is evidence of it | required |
| plan-delivered | Each deliverable the plan's scope names (each change, each named file, each promised test, doc, or changelog entry), read against the diff, and every deferral or deviation the plan and the PR description state (evidence guide: Plan fidelity) | Passes if every deliverable the plan names appears in the diff, or its absence is stated both in the plan (a deviation or deferral note) and in the PR description. A deliverable the plan itself made conditional ("if it proves messy it will be deferred with a note") is met by a description that states the deferral. Fails if a named deliverable is missing from the diff and the description does not say so, or if the diff implements a different approach than the plan names (another mechanism, another file, a dependency bump in place of the planned code change) with no deviation note | required |
| description-matches-diff | Every statement in the PR title and description about what the change does, what it includes (tests, docs, changelog, files touched), and how faithful it is to the plan ("implements the plan exactly", "in full", "nothing else changed"), read against the diff and the commit list (evidence guide: Plan fidelity) | Passes if every such statement is true of the diff at the level a reviewer acts on: each claimed inclusion (a file, a docs update, a changelog entry, a test of the fix) is a hunk in the diff, each described behavior change is what the hunks do, and each fidelity claim holds because the diff carries no unplanned hunk and lacks no planned deliverable. Imprecise wording about how the claimed work is arranged (how many functions it touches, which test case covers which input, a count that is off by one) does not fail when the claimed work itself is in the diff. Statements about test results are graded by the test checks, not here. Fails if the title or description claims work the diff does not contain (a docs update, a changelog entry, a test), describes a behavior change the hunks do not make, or makes a fidelity claim ("exactly as planned", "nothing else changed") while the diff carries unplanned work or lacks planned work | required |
| repro-evidence-decisive | The test evidence section and any before/after in the description, read against the plan's test plan (each repro re-run it names, each failure mode, and the expected-after it states) and the repro evidence in the plan context (evidence guide: Test evidence) | Passes if both hold. (1) Every reproduced failure, meaning each trigger or failure mode the repro evidence shows failing and the test plan says to re-run, is run on the changed code with its observed result shown: pasted output, or the exact command or steps with the specific observable each produced (the error message gone, a named file listed or not listed, an exit code, a value, a toast's text). The observed result is the expected-after the plan states, and the before is shown in the evidence or the description or is the plan's own repro evidence. (2) Every other item the test plan names (a control, a smoke check, a scenario for new behavior the fix adds, a parity comparison) has its outcome reported, in a sentence or by a named passing test. Fails if a reproduced failure is characterized instead of shown ("works now", "fixed on my machine", "ran it for a while with no errors", "too small to need testing", a result with no command or steps behind it); if it is run with a different input or path than the plan's trigger (a control, a simpler case that never triggered the bug, a different input shape, a path the fix does not change); if a reproduced failure or a test-plan item is never mentioned; or if the observed after differs from the expected-after. A new unit test passing does not stand in for re-running a reproduced failure | required |
| repo-checks-reported | The test evidence section and the description, read against every suite or check command the plan's test plan names and every check the repo's stated asks say a PR must pass (evidence guide: Test evidence) | Passes if every such suite or check has its outcome reported under its command or suite name ("`pytest tests/unit` passes (120 passed)", "lint and format clean"), and every reported failure carries a stated reason that is not the change itself (no tests exist yet for that suite, a failure already present on the default branch). A check that runs only after the PR is opened (hosted CI) is not required before submission. A plan and repo that name no suite or check pass. Fails if a named suite or check is never reported, if an outcome is asserted without saying which suite ran ("all tests pass") while the plan or repo names one, or if a reported failure is caused by the change or has no stated reason | required |
| diff-free-of-debris | Every added line, every hunk in the diff, and every commit message (evidence guide: Diff quality) | Passes if the diff contains none of these: (1) debug output added for the author's own diagnosis (a print, eprintln, console.log, or log call marked DEBUG or DBG, or one dumping internal state that the plan does not name as a user-facing message); (2) commented-out code, including a commented-out first attempt "kept for reference"; (3) dead code: a function or variable the diff adds that nothing calls, or one marked unused, `_unused`, or `allow(dead_code)`; (4) a TODO, FIXME, or XXX the diff adds; (5) a hunk, or a run of lines inside one, that only reformats, re-indents, reorders or regroups imports, or removes and re-adds identical lines in code the fix does not otherwise change; (6) a commit message that names no change ("wip", "fix", "stuff", "cleanup while debugging"). Prose comments that explain the change pass, and so do unchanged lines re-printed inside the same statement as a planned edit. Fails if any one of (1) to (6) appears | required |
| template-and-asks-met | The repo facts' pull-request line (template sections, checklist items, required lines, required file entries, title or commit conventions, required tests) and contribution-policy line, read against the PR title, description, commits, and diff; in live mode, the repo's PR template, `docs/CONTRIBUTING.md`, and the house rules in `scope.md` (evidence guide: Standards and comms) | Passes if every ask the repo states for a pull request is met for this change: each template section or checklist item appears with content specific to this PR (a prose answer to an item counts the same as a ticked box); a required issue-reference line ("closes #N", "fixes #N") carries the issue number; a required file entry (changelog, whatsnew, release note) is a hunk in the diff; a stated title, branch, or commit-message convention is followed; tests the repo asks for are in the diff. An ask that cannot apply to this change (screenshots for a change with no UI, schema notes for no schema change) passes when the description marks it not applicable or the change plainly has nothing for it. A repo with no template and no stated asks passes. Fails if any stated ask is unmet: a template section or checklist item missing, left as the template's placeholder, or ticked while untrue; a required reference line or file entry missing; a stated convention broken | required |
| ai-disclosure-met | The repo facts' contribution-policy line and any AI policy it names, read against the PR description; in live mode, the repo's AI policy if it has one and the course's AI-use disclosure ask (evidence guide: Standards and comms) | Passes if the stated policy places no AI-disclosure requirement on pull requests, or if the description contains a disclosure, in the author's own words, that AI was used and states everything the policy says a disclosure must state (for example the tool used and the extent of the assistance). Treat every package as AI-assisted work, so a policy that requires disclosure is never met by silence. Policy requirements a reader cannot check from the text (that the human in the loop understands the work) pass when the disclosure asserts them. Fails if the policy requires disclosing AI use and the description has no disclosure, or has one that leaves out something the policy says it must state | required |

## Verdict rule

Accept only if every required check passes.
Any required check graded `fail` rejects the package.
An `unclear` grade counts as `fail` on every check, so an `unclear` on any check also rejects.
There are no preferred checks, so every check can change the verdict.
A PR that delivers less than the plan, or departs from it, is not a failure in itself: plan-delivered and diff-within-plan pass it when the plan's notes and the description both state the shortfall or deviation, and every other check grades only the work the PR takes on.
